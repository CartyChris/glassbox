## Ollama from the hosted site (the real bug)
- `localFetchOpts()` declared `targetAddressSpace:'local'` for 127.0.0.1. Since Chrome's Local Network Access split, `local` = private
  LAN and 127.0.0.1 = `loopback`; a mismatched declaration fails the request before it is sent ("Request had a target IP address
  space of `local` yet the resource is in address space `loopback`"). Measured in real Chrome 156. Every Ollama AND bridge request
  from glassbox-jet.vercel.app failed, so the app said "No Ollama server answered" and no suggested fix could work.
  Now: `addrSpace(url)`; only a private-LAN target is declared; loopback is inferred by Chrome.
- With that fixed, the app correctly reports "running but refuses this site" (Ollama 403s an origin missing from OLLAMA_ORIGINS)
  and shows one macOS paste that adds the site, saves a login item (`com.glassbox.ollama-origins`, re-applies the setting at
  login and restarts Ollama if it came up first and still 403s), stops BOTH servers (menu-bar app + any terminal `ollama serve`),
  reopens the app and prints HTTP 200. Undo command shown beside it. On a Mac the "not running" advice is `open -a Ollama`, not
  `ollama serve` (which starts the second server that never sees launchctl).
- Verified: real Chrome on the production origin (routed to the new build) — old build: all three addresses rejected; new build:
  correct diagnosis; against an Ollama that allows the origin: "Connected — 4 local models". The shipped command was run under a
  fake HOME with stubbed launchctl/pkill/open: valid plist (`plutil -lint`), parseable login script. It was NOT installed on this
  Mac (permission system refused the persistent login item); the person runs it once.
